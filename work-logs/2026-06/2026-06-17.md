**Work Log — IISS-487: Meridian SRE Dashboard Restructuring**

**1. Redis/Valkey Row Architecture — 12-Panel Restructure Across 3 Visual Rows**
The Redis/Valkey monitoring row (Row 11) was comprehensively restructured to provide a cohesive SRE-focused view of cache infrastructure. The new layout organises 12 panels across three visual rows: a resource inventory table, CPU metrics (average and maximum), memory metrics (average and maximum), cache hit rate, replication lag, active connections, latency distribution, and network throughput panels. This structure replaces the previous layout and provides operators with a complete operational picture of Redis/Valkey cluster health without requiring navigation to external dashboards.

**2. Redis Deprecated Plugin Removal — redis-datasource Panels Decommissioned**
Three panels using the deprecated redis-datasource plugin were identified and removed from the Redis row: the Redis Info panel, Slow Log panel, and Total Keys panel. These panels relied on direct Redis protocol queries that are no longer supported in the current Grafana environment. Their removal eliminates stale data display and reduces confusion around which panels are actively maintained versus legacy artifacts.

**3. Performance Row — Redis CPU Panel Replacement with Memory & Cache Hit Rate**
The Redis CPU panel in the Performance row (Row 2) was replaced with two operationally critical bargauge panels: Memory Usage and Cache Hit Rate. These metrics were identified through SRE consultation as the two most important indicators of Redis cluster health and performance degradation. The CPU metric, while useful, is secondary to memory pressure and cache efficiency for operational decision-making.

**4. Performance Row Panels — Comprehensive Description Documentation**
All 18 panels in the Performance row were updated with descriptive text explaining what each metric represents, how it should be interpreted, and the operational thresholds at which intervention is typically required. These descriptions are displayed as panel headers and tooltips, providing context to operators who may be unfamiliar with specific metrics or who are responding to alerts outside their primary domain of expertise.

**5. Cache Hit Rate Bargauge — Sort Order Correction for Worst-First Display**
The cache hit rate bargauge panel was displaying results in an arbitrary order that did not prioritise operator attention. A sortBy transformation was added to order results by hit rate in ascending order, placing the lowest-performing cache instances at the top of the panel. This worst-first ordering ensures that operators scanning the panel quickly identify the cache instances most in need of investigation.

**6. OpenSearch Row Restructure — 9 Panels to 12 SRE-Focused Panels**
The OpenSearch monitoring row (Row 13) was restructured from 9 panels to 12 panels with a focus on SRE operational requirements. The new layout includes four cluster status tables displaying counts of nodes in Green, Yellow, Red, and Not Available states, plus eight metric panels covering CPU (average and maximum), JVM memory, indexing rate, search latency, write blocking events, snapshot failures, and HTTP 5xx error rates. This structure provides both cluster health visibility and detailed performance metrics in a single view.

**7. Grafana Transformation Pitfall — Single-Step Reduce Silent Row Dropping**
During OpenSearch panel development, a critical Grafana transformation behaviour was discovered: applying a single-step reduce transformation silently drops rows that do not match the reduction criteria, without warning or error indication. This caused panels to display incomplete data without any visual indication of data loss. The issue was resolved by implementing a two-step reduce pattern: first reduceFields to aggregate metrics, then seriesToRows to reshape the result. This pattern is now documented as the standard approach for all multi-series reductions.

**8. Known Limitation #8 — Grafana Reduce Transformation Row Dropping**
The single-step reduce row-dropping behaviour was formally documented as Known Limitation #8 in the project's limitations register. The documentation includes the root cause (Grafana's reduce function silently filters rows), the workaround (two-step reduce pattern), and guidance for future panel developers to avoid this pitfall. This documentation ensures the team does not re-discover this issue in future development cycles.

**9. FilterByValue Transformation — Float/Integer Type Mismatch Resolution**
A subtle type mismatch was identified in filterByValue transformations across multiple panels. CloudWatch returns metric values as floats (e.g., 1.0), but the equal comparator in Grafana expects integer values (e.g., 1), causing filters to silently fail. The fix was to replace equality comparisons with a greater-than threshold (> 0.5), which correctly handles both float and integer representations. This pattern was applied consistently across all affected panels.

**10. OpenSearch "Not Available" Panel — False Positive Elimination**
The OpenSearch "Not Available" cluster status panel was generating false positives by filtering on ClusterStatus.green=0, which inadvertently caught clusters in Yellow or Red states. The filter logic was corrected to MIN(Nodes)=0, which specifically identifies clusters with zero available nodes — the true definition of "Not Available" state. This change eliminates spurious alerts and improves the accuracy of cluster health reporting.

**11. OpenSearch JVM Memory Pressure — Performance Row Addition**
A new bargauge panel displaying OpenSearch JVM Memory Pressure was added to the Performance row (panel 19). JVM memory pressure is a leading indicator of OpenSearch cluster degradation and is critical for SRE decision-making around scaling and resource allocation. The panel uses the same colour thresholds and display conventions as other performance metrics for visual consistency.

**12. Health Overview Row — Complete Panel Renumbering & Restructure**
The Health Overview row (Row 1) underwent a comprehensive restructure including renumbering all panels from 01 to 14 to reflect the current layout. All panels were updated with descriptive text explaining their purpose. The RDS multi-instance display was fixed using the two-step reduce pattern to correctly aggregate metrics across multiple database instances. OpenSearch cluster status was split into separate Yellow and Red count panels for clearer health signalling.

**13. Health Overview Alarm Panels — Naming & Colour Standardisation**
The alarm panels in the Health Overview row were renamed from generic "Alarms" labels to "Alerts Critical" and "Alerts Warning" to clearly distinguish severity levels. Threshold colours were corrected so that panels display green when the alert count is zero (healthy state), transitioning to red or yellow as alert counts increase. This colour convention aligns with standard SRE dashboard practices and reduces operator confusion.

**14. Health Overview Deep Links — Post-Restructure Navigation Correction**
Following the Health Overview row restructure, all 14 deep link references within the row were audited and corrected to point to the new panel IDs. Deep links are used to navigate from summary panels to detailed views; broken deep links would have silently failed, leaving operators unable to drill down into specific service health details. All 14 links were verified to route correctly to their target panels.

**15. Neptune Platform Naming Limitation — "N/A" Text Fallback**
Neptune panels were displaying "No data" when the platform naming variable was not available, creating a confusing user experience. A noValue text override was added to display "N/A" instead, clearly indicating that the data is not applicable rather than unavailable. This addresses a known limitation in the platform variable handling without requiring infrastructure changes.

**16. ECS 5xx Error Panel — Sparse Metric Zero Display**
The ECS 5xx error panel was failing to display "0" when no errors were present, due to CloudWatch's sparse metric behaviour (omitting zero values from time series). A transformation was added to explicitly set the panel value to "0" when the metric is absent, ensuring operators see a clear zero-error state rather than an ambiguous empty panel. This improves the visual clarity of the error monitoring dashboard.

**17. Git Workflow Steering — 3-Way Merge Strategy Rule**
The project's git workflow steering configuration was updated to enforce a 3-way merge strategy for all pull requests: no fast-forward merges, no squash commits, and preservation of full commit history. This strategy ensures that the commit history accurately reflects the development process, making it easier for future developers to understand the evolution of the codebase and to identify when specific changes were introduced.
