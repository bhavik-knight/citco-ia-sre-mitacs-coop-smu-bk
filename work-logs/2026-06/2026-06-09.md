**Work Log — IISS-487: Meridian SRE Dashboard Alarm Panels & EC2 Monitoring Row**

**1. Alarm State History Panel — Legend Explanation Documentation**
A legend explanation was added to the Alarm State History panel description, clarifying what each colour band and state transition in the timeline represents. Operators unfamiliar with the CloudWatch alarm state model benefit from inline context explaining the distinction between ALARM, OK, and INSUFFICIENT_DATA states as they appear in the historical timeline, reducing the likelihood of misinterpretation during incident review.

**2. Health Overview Row — Alarms Stat Panel Addition**
An Alarms stat panel was added to the Health Overview row to surface the current alarm state directly in the top-level dashboard summary. This gives operators an immediate signal of overall alarm health without needing to scroll to the dedicated alerts row, supporting faster initial triage when the dashboard is first opened during an incident or during routine operational checks.

**3. Alarms Stat Panel — Worst State Display with Label Mapping**
The initial Alarms stat panel implementation was displaying raw numeric state values rather than human-readable labels. The panel was fixed to show the worst current alarm state using a label mapping that translates CloudWatch's numeric state representation into the corresponding text labels: ALARM, OK, and INSUFFICIENT_DATA. This ensures operators see a meaningful status indicator rather than an opaque numeric value.

**4. Alarm Count Publisher Lambda — WorstAlarmState & TotalAlarmCount Metrics**
Two new metrics were added to the alarm count publisher Lambda: WorstAlarmState and TotalAlarmCount. WorstAlarmState publishes the most severe current alarm state as a numeric value that the Health Overview stat panel can query, while TotalAlarmCount provides a count of all alarms regardless of state. These additions give the dashboard the CloudWatch metric data it needs to power the alarm health panels without requiring direct CloudWatch alarm API queries from Grafana.

**5. Health Overview — Critical & Warning Alarm Count Stat Panels**
The alarm health representation in the Health Overview row was extended with separate stat panels for critical and warning alarm counts. Splitting the alarm summary into two distinct severity panels allows operators to immediately distinguish between critical conditions requiring urgent response and warning conditions requiring monitoring, rather than seeing a single aggregated alarm count that obscures severity distribution.

**6. AMG Single Query Limit — Alarm Panel Split Resolution & Documentation**
During implementation it was discovered that Amazon Managed Grafana enforces a single SQL query per panel, preventing the original design of combining critical and warning counts in one panel. The panel was split into two independent stat panels — one for critical alarms and one for warning alarms — each backed by a single SQL query. This architectural constraint was documented to inform future panel design decisions and prevent the same issue from being encountered again.

**7. Alarms Stat Panel & State-Timeline Panel — Test Coverage**
Unit and validation tests were written for both the Alarms stat panel and the state-timeline panel. The tests cover panel type assertions, field configuration, label mapping correctness, and display option validation. Adding test coverage for these panels ensures that future modifications to the alarm visualisation configuration are caught by the test suite before reaching the DEV environment.

**8. Alarm Metric Publishing Pipeline — End-to-End Validation**
The full alarm metric publishing pipeline was validated end-to-end: from the publisher Lambda emitting WorstAlarmState and TotalAlarmCount metrics to CloudWatch, through to the Grafana stat panels correctly consuming and displaying those metrics. This validation confirmed that all components of the alarm health feature are functioning correctly together before the changes were committed for deployment.

**9. Redis Row 10 — Panel Configuration Fix**
A configuration issue in the Redis row (Row 10) panel definitions was identified and resolved. The fix restored correct metric queries and display settings that had been disrupted during earlier restructuring work, ensuring the Redis row renders accurately and consistently with the panel configuration standards applied across other service rows.

**10. Kiosk Mode URL — Sidebar Hide Documentation**
The Grafana kiosk mode URL parameter for hiding the sidebar on dashboard load was identified and documented. This is particularly useful for operational display screens and NOC environments where the Grafana navigation sidebar consumes screen real estate that would be better used for dashboard content. The documentation covers the URL parameter syntax and the scenarios in which kiosk mode is recommended.

**11. EC2 Monitoring Row — Health Stat & Performance Overview Panels**
A new EC2 monitoring row was added to the dashboard, comprising a health stat panel showing overall EC2 instance health and performance overview panels covering CPU utilisation across the EC2 fleet. EC2 is a foundational infrastructure layer for the Meridian platform, and its absence from the dashboard represented a visibility gap for SRE operators monitoring overall platform health. The new row follows the same structural conventions as other service rows.

**12. EC2 Instance Mapper Lambda — Per-Platform Instance Selection**
An EC2 instance mapper Lambda was implemented to support per-platform EC2 instance filtering in the dashboard. The Lambda queries the EC2 API to identify instances belonging to the current platform and publishes the results in a format that Grafana dashboard variables can consume. This enables the dashboard to display EC2 metrics scoped to the relevant platform instances rather than showing all EC2 instances in the account.

**13. Per-Platform EC2 Dashboard Variables — ec2_meridian & Dynamic ec2_instances**
Per-platform EC2 dashboard variables were added, with ec2_meridian defined to hold the list of EC2 instances associated with the Meridian platform. A dynamic ec2_instances variable was also implemented using a CloudWatch dimension query to automatically populate the instance list as instances are added or removed, without requiring manual dashboard updates. Panel queries were updated to reference these variables, ensuring EC2 metrics are correctly scoped to the relevant platform context.

**14. EC2 Panels — WHERE Clause Removal & Comprehensive Audit**
EC2 panel queries were found to include a WHERE clause that was incorrectly filtering out instances, resulting in incomplete or empty panel displays. The clause was removed to delegate filtering responsibility to the dashboard variable. A follow-up audit revealed that the initial fix had missed several panels, so a thorough review of all EC2 panel query definitions was conducted and the WHERE clause was removed from every remaining affected panel, ensuring consistent query behaviour across the entire EC2 row.

**15. EC2 CloudWatch Dimension Query Validation**
The CloudWatch dimension queries powering the dynamic ec2_instances variable were reviewed and validated to confirm they return the correct instance set for each platform. The validation confirmed that per-platform filtering operates as expected and that no instances from unrelated platforms are included in the variable's result set, providing confidence in the accuracy of the EC2 panels before deployment.

**16. EC2 Row Position & Health Panel Ordering**
The EC2 row was repositioned to appear before the ECS Infrastructure row, reflecting the logical infrastructure hierarchy where EC2 instances underpin ECS cluster capacity. The EC2 CPU health panel in the Health Overview row was simultaneously repositioned to appear after the Lambda health panel and before the ECS section, ensuring the health summary row presents service indicators in a sequence consistent with the full dashboard layout.

**17. DEV Deployment — EC2 Monitoring Row & ProvisionerVersion Bump**
All EC2 monitoring changes were deployed to the DEV Grafana environment, including the new EC2 row, the instance mapper Lambda, the dashboard variables, and the Health Overview row reordering. The ProvisionerVersion was incremented to trigger a full Lambda provisioner refresh, ensuring all changes were applied to the live dashboard without the provisioner treating the update as a no-op.

**18. Health Row Per-Panel Folder Structure — Initial Refactoring**
The Health Overview row was refactored from a single monolithic row_01_health.json file into individual JSON files, one per panel. This is the first row to be split under the new per-panel folder structure and serves as the reference implementation for the pattern to be applied across all remaining rows. Each panel file is named consistently to reflect its panel number and content, making individual panels independently editable and reviewable in version control.
