1. ECS APIs Row — Target Group Name Legend Fix
   All panels in the ECS APIs row were displaying raw CloudWatch dimension values in their legends rather than human-readable target group names. Each affected panel was updated to extract and display the target group name, significantly improving readability during incident triage where operators need to quickly identify which target group a metric belongs to without decoding raw dimension strings.
2. Request Throughput Panel — Legend Cleanup via renameByRegex
   The request throughput panel legend was updated to display clean target group names using a renameByRegex transformation. The previous legend entries contained the full dimension path, making it difficult to distinguish between target groups at a glance. The regex transformation extracts only the meaningful target group identifier, producing a concise and consistent legend across all throughput series.
3. HTTP 4xx/5xx Error Panels — Target Group Name Standardisation
   The HTTP 4xx and 5xx error rate panels were updated to apply the same legend cleanup approach as the throughput panel. Both panels now display clean target group names rather than raw dimension values, ensuring visual consistency across all ECS APIs row panels and making it straightforward to correlate error rates with specific target groups during incident investigation.
4. Response Time Percentile Panels — ALB Name Legend Correction
   The p50, p95, and p99 response time panels were displaying raw ALB dimension values in their legends. A renameByRegex transformation was applied to each panel to extract and display clean ALB names. This is particularly important for latency panels, where operators need to quickly identify which load balancer is exhibiting elevated response times without parsing lengthy dimension strings.
5. MSK Resource Table — Deep-Link Cluster Search Filter Correction
   The MSK resource table deep-link was pointing to an incorrect URL that did not filter by cluster. The link was updated to use the cluster search filter parameter in the MSK Console URL, ensuring that clicking through from the dashboard navigates directly to the relevant cluster view rather than an unfiltered resource list. This reduces the number of steps required to reach the relevant resource during operational investigations.
6. Feature Branch Merge — link-panels into Release
   The feature/IISS-487-link-panels branch was merged into release/IISS-487-sre-observability following successful validation of all deep-link and legend fixes. The merge consolidates the panel linking work into the release baseline, making it available for UAT promotion alongside other IISS-487 changes.
7. AWS Console Deep-Link Limitations — Documentation & Workarounds
   A documentation guide was produced covering the known limitations and workarounds for AWS Console deep-links from Grafana panels. The guide addresses the distinction between services that require ARN-based URL construction versus those that accept dimension values directly, and documents the specific formatting requirements for each supported service. This reference prevents future developers from encountering the same trial-and-error process when implementing deep-links for new service rows.
8. Infinity Datasource Plugin — Documentation Guide
   A dedicated documentation guide for the Infinity datasource plugin was written and cross-linked from the AWS Console deep-link limitations document. The guide covers configuration, supported query types, and usage patterns relevant to the Meridian dashboard context. Linking the two documents together provides a complete reference for developers working on console navigation and external data integration features.
9. ECS Bargauge Deep-Links — Direct ECS Console Service Navigation
   Deep-links were implemented on the ECS bargauge panels so that clicking a bar representing a high-CPU service navigates directly to that service's page in the ECS Console. The links use ${__data.fields.Field} URL templates to dynamically construct the correct console URL based on the service name displayed in each bar. This allows operators to move from identifying a resource-intensive service on the dashboard to investigating it in the console in a single click.
10. Bargauge Deep-Link Technique — Documentation & Cross-Linking
    A technique guide was written documenting the bargauge deep-link implementation pattern using ${__data.fields.Field} URL templates. The guide explains how to construct dynamic console URLs from bargauge field values, covers edge cases such as URL encoding requirements, and provides worked examples for ECS and SQS. The guide was cross-linked to all related documentation to ensure it is discoverable by developers implementing deep-links on future service rows.
11. SQS Bargauge Deep-Links — Queue Depth & Message Age Console Navigation
    Deep-links were added to both SQS bargauge panels — Top Queues by Depth and Top Queues by Message Age. Clicking a bar on either panel navigates directly to the corresponding queue in the SQS Console, using the same ${__data.fields.Field} URL template pattern established for ECS. This gives operators immediate access to queue configuration and message details when investigating depth or age anomalies surfaced by the dashboard.
12. EC2 Panels — Console Deep-Links, Layout Positioning & Memory Monitoring Limitation
    EC2 panels with AWS Console deep-links were added to the dashboard, and EC2 was repositioned before ECS in the dashboard layout to reflect the logical infrastructure hierarchy. A documentation entry was also written covering the EC2 memory monitoring limitation — specifically that CloudWatch does not collect memory metrics from EC2 instances by default and that the CloudWatch Agent must be installed and configured to enable memory visibility. This limitation is documented to set accurate expectations for operators reviewing EC2 panels.
13. DocumentDB Row — 4+4 Panel Layout Restructure & Freeable Memory Addition
    The DocumentDB row was restructured into a 4+4 panel layout with each panel set to width 6, providing a balanced and consistent visual grid. A freeable memory bar chart panel was added to give operators visibility into available memory headroom across DocumentDB instances. A metric statistics documentation guide was also written to explain the statistical aggregation methods used across DocumentDB panels, supporting both current operators and future dashboard maintainers.
14. Performance Row — MSK Broker Disk & DocumentDB Freeable Memory Bargauges
    Two new bargauge panels were added to the Performance row (Row 2): MSK Broker Disk Usage and DocumentDB Freeable Memory. These metrics were identified as operationally significant additions to the performance overview, providing at-a-glance visibility into storage pressure on MSK brokers and memory availability on DocumentDB instances alongside the existing compute and latency metrics.
15. Performance Row — MSK & DocumentDB Panel Grid Position Overlap Fix
    Following the addition of the MSK Broker Disk and DocumentDB bargauge panels, overlapping gridPos x-coordinates were identified that would have caused panels to render on top of one another. The grid positions were audited and corrected across the affected panels, restoring the intended layout and ensuring all Performance row panels render in their correct positions without overlap.

The restructure improves visual consistency when scrolling through the dashboard and ensures RDS panels align with the grid conventions established for DocumentDB and other database service rows.
