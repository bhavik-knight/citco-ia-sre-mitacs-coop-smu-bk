\section{Week 2}
\label{sec:week2}

With access requests progressing through the approval queue, Week~2 shifted to intensive self-directed AWS learning. Dr.\ Pawan had confirmed that the part-time schedule would continue through mid-April while my university courses were running, so I structured these early weeks around building the AWS knowledge foundation I would need before taking on my first JIRA tickets.

I completed a structured study of the full AWS database portfolio, working through both official AWS documentation and hands-on exploration via the team's Confluence resources. For relational databases I studied Amazon RDS (including Single-AZ and Multi-AZ high availability configurations, read replicas, and automated failover), Amazon Aurora (auto-scaling clusters and the performance advantages over standard RDS for OLTP workloads), and Amazon Redshift (columnar storage, Redshift Spectrum for semi-structured data, and its positioning as an OLAP warehouse rather than a transactional database). For NoSQL options I studied DynamoDB (schema-less design, partition key selection, and the tradeoffs between strongly and eventually consistent reads) and DocumentDB (MongoDB-compatible API, collections vs tables, and its use at Citco for document-oriented workloads).

The Neptune graph database study was particularly relevant. I learned that CitcoWorks uses a Neptune graph database to store the full L1-to-L5 entity hierarchy of client, fund, and process relationships that governs event routing across the IA platform. I studied both Gremlin (property graph traversal using vertex/edge/property model) and SPARQL (RDF triple pattern matching for semantic data integration), understanding when each is appropriate: Gremlin for application-level graph traversal, SPARQL for standards-based semantic integration. This distinction proved relevant when I later worked on the RPA LLM Agent, which uses Neptune as a potential graph layer for Hybrid Graph-RAG retrieval.

I also studied Amazon TimeStream (serverless time-series database for IoT and operational metrics), Amazon QLDB (immutable ledger database for audit-grade transaction logs), and Amazon ElastiCache including both Redis (advanced data structures, pub/sub messaging, geospatial support, cluster mode with multiple primary nodes) and Memcached (simpler multi-threaded caching without data replication). The Redis study was directly applicable to the dashboard work: the IA platform uses Redis/Valkey clusters for caching, and I built the Redis monitoring row in Week~11.

CloudWatch and CloudFormation consumed the second half of Week~2. For CloudWatch I studied the CMAA operational cycle (Collect, Monitor, Act, Analyze), the difference between EC2 1-minute detailed monitoring and 5-minute basic monitoring, log retention policy configuration, alarm types (metric alarms for single metrics, composite alarms for aggregated state), and EventBridge integration for alarm state routing. For CloudFormation I covered the core IaC primitives: template structure (YAML and JSON), stack lifecycle management, and change sets for controlled update previewing. I immediately applied this knowledge in Week~3's first dashboard ticket.

By the end of Week~2, I had a working knowledge of the full AWS services landscape used by the IA platform, and I understood the CloudWatch and CloudFormation primitives I would be using extensively from Week~3 onward.

\section{Week 3}
\label{sec:week3}

Week~3 was when I transitioned from learning to active delivery, with my first assigned task: the CTI CloudWatch Pipeline Dashboard. This was a CloudWatch pipeline health dashboard for the \texttt{rpacfs1-cais-pricing-extract-genai-infrastructure} repository, specifically targeting the CAIS Pricing Extract (CTI) submission pipeline.

On March~30 I began implementing the dashboard. I first added CloudWatch metrics instrumentation to the \texttt{rpacfs1-cais-pricing-extract-genai-infrastructure} codebase to track CTI submission activities within the pipeline. Rather than placing metrics calls inline throughout the business logic, I refactored the instrumentation into a dedicated metrics module, which made the metrics configuration testable and maintainable independently of the pipeline logic. I created the Pipeline Health Dashboard itself with CloudWatch native widgets covering the core health signals for the CAIS pricing extract workflow. I updated the \texttt{.gitignore} to exclude virtual environment directories, pytest cache, and test artifacts --- basic repository hygiene that the codebase was missing. I also updated the dashboard configuration to meet the acceptance criteria I had been given: 1-hour metric granularity, a 7-day time range, and auto-refresh enabled so the team would see live pipeline status without manual page refreshes.

On March~31, I added a technical investigation layer: a CloudWatch Logs Insights widget that enabled operators to drill into raw Lambda execution logs when the health metrics indicated a problem. The Logs Insights widget used a pattern-matched query against the \texttt{/aws/lambda/} log group prefix to surface error patterns directly in the dashboard, rather than requiring the operator to navigate to CloudWatch Logs and write a query manually. I added screenshots of the Logs Insights query setup to the PR documentation so the team could reproduce the configuration in other environments.

On April~1, I completed the testing phase. I wrote unit tests for the Logs Insights query functionality, CloudFormation template validation tests (checking that the template schema was valid before deployment), and ran the full test suite to confirm no regressions. I also applied code quality improvements identified during writing the tests: moving all import statements to the top of files following Python best practices, and adding type hints to function signatures to enable better IDE support and early error detection.

By the end of Week~3, the CTI CloudWatch Pipeline Dashboard was ready for PR review. The dashboard covered the CTI pipeline health signals, the Logs Insights investigation widget was functional, the test suite was passing, and the repository was in a clean state for code review. This was my first complete delivery cycle at Citco --- task assignment to implementation to tests to PR --- and it established the quality baseline I would maintain for all subsequent work.

\section{Week 4}
\label{sec:week4}

In Week~4, the focus was on completing the IA Lambda Monitoring Dashboard,
addressing PR review feedback, and delivering structured Lambda inventory
documentation on Confluence.

\textbf{Merging the CTI Dashboard and Pivoting to Lambda Monitoring:} 
The week opened on
April~6 with the successful merge of CTI CloudWatch Pipeline Dashboard
into the \texttt{release/SRE} branch, closing the first JIRA ticket of
the co-op placement. I immediately transitioned to IA Lambda Monitoring Dashboard, which required
building a monitoring solution covering all 51 Lambda functions across
the \texttt{rpacfs1} and \texttt{ia-bpo} platforms. Unlike the CTI
dashboard, which targeted a single pipeline, IA Lambda Monitoring Dashboard needed to serve
the entire IA Lambda fleet with a single unified view.

\textbf{Dashboard Architecture and Widget Design:} 
I designed the dashboard
using a modular YAML widget architecture where each widget type lives in
its own file, allowing independent updates without touching surrounding
logic. Widgets covered five monitoring domains: filter info with inline
usage instructions, overview metrics (Total Invocations, Errors,
Throttles across all functions), error analysis (bar charts and a
CloudWatch Logs Insights investigation widget), duration metrics
(Average, Max, and P99 latency), and operational health metrics
(cold starts, concurrency, throttling, and memory utilization).
The unit test suite reached 21 tests covering dashboard builder
validation and widget contract enforcement.

\textbf{PR Review and Refinement:} 
On April~8, Mr.\ Leung conducted
a detailed PR review. Feedback focused on widget layout usability and
filter propagation behavior. I addressed all comments, refined the
widget grid, and added test cases for edge cases identified during the
review. This review interaction introduced me to the team's standard for
dashboard quality: functional correctness was necessary but not
sufficient---the operational user experience mattered equally.

\textbf{Confluence Lambda Inventory:} 
In parallel with the
PR review, I created Lambda Inventory documentation as a subtask to document the Lambda
inventory on Confluence. The published page cataloged all 51 functions
with trigger mappings (S3, SQS, EventBridge, API Gateway), memory
configurations, timeout settings, runtime versions, and budget code
allocations for cost tracking. This page became the authoritative
reference for the team during subsequent dashboard and support work.

By the end of Week~4, The CTI CloudWatch Pipeline Dashboard work was completed and merged, IA Lambda Monitoring Dashboard
delivered a 51-function Lambda dashboard with a passing test suite, and
the Lambda inventory documentation was live on Confluence---completing
the part-time phase and setting the stage for full-time engagement.

The Dashboard Extension and API Refactoring was completed this week and the Grafana AMG Dashboard scope was formally defined.

By the end of Week~5, I had completed the formal KT programme, delivered
a multi-dashboard architecture refactor, and directly witnessed the production

\section{Week 6}
\label{sec:week6}

In Week~6, the focus was on extending the CloudWatch monitoring platform
beyond Lambda to EC2, ECS, and EKS resources, creating the centralized
\texttt{ia-resources-monitoring} repository, and formally creating
the centralized AMG dashboard story.

\textbf{Dashboard Extension and API Refactoring:} 
The week
opened with Dashboard Extension and API Refactoring work: adding a metric filters generator, implementing
dashboard export functionality with per-widget CSV files and a combined
XLSX report, and converting the Lambda registry from a FastAPI service
to a Flask application with Swagger documentation. I renamed
\texttt{lambda\_registry\_api} to \texttt{resources\_monitoring\_api}
to reflect its broader scope and added an S3 export endpoint with
versioned Lambda list saving. Trigger source detection was added,
identifying whether each Lambda function is invoked by SQS, API Gateway,
or EventBridge. The test suite reached 262 passing tests with a clean
pyright status.

\textbf{EC2, ECS, and EKS Resource Discovery:} 
I extended the API to cover EC2 instances, ECS services, and EKS
clusters. During EC2 discovery I identified the \texttt{rpacfs1} tagging
inconsistency---the fleet uses \texttt{BudgetCode="CFS/RPA"} rather than
the expected \texttt{"rpacfs1"} value---and introduced the
\texttt{AppName} fallback pattern as the standard workaround. EC2 response
models were enriched with \texttt{availability\_zone} and \texttt{tags}
fields. The \texttt{registry} package was refactored into per-resource
sub-modules for long-term maintainability.

\textbf{ia-resources-monitoring Repository Creation:} 
On
April~24---the most commit-dense day of the co-op placement with 39 commits
across two repositories---I set up the centralized \texttt{ia-resources-monitoring}
repository. All three monitoring packages (Lambda, EC2, and the API)
were migrated from \texttt{rpacfs1-cais-pricing-extract-genai-infrastructure}
into this dedicated repository. Code quality tooling was established:
Ruff linting, mypy type checking, deptry dependency hygiene, and
pre-commit hooks. The \texttt{ia\_paths.py} module was introduced to
eliminate all \texttt{sys.path.insert} calls and a unified
\texttt{main.py} CLI entry point provided access to all deployment
and dashboard generation commands. The \texttt{release/SRE} branch
was merged to master, making this the first production deployment
from the new repository.

\textbf{Story Creation:} 
Following the Week~5 Meridian Incident
and the emerging need for a platform-wide observability solution, I met
with Mr.\ Deotale to formally scope and create the Centralized Amazon Managed Grafana (AMG) Dashboard --- the
Grafana AMG Infrastructure Monitoring Dashboard. I created the story
with requirements drafted to cover all Meridian-platform AWS services
and address the MSK consumer lag gap that had caused the incident.

By the end of Week~6, the CloudWatch monitoring platform covered four
resource types, the centralized repository was established and
production-deployed, and The Centralized Amazon Managed Grafana (AMG) Dashboard was formally created with an
agreed scope and priority.

\textbf{Technical Challenges Resolved:} 
Two infrastructure issues were
resolved during the migration day. The \texttt{moto[all]} dependency
triggered SSL certificate download failures on Windows; switching to
specific service extras (\texttt{moto[s3,lambda,ec2]}) resolved this.
CloudFormation YAML files using \texttt{!Sub} and \texttt{!Ref} tags
failed the \texttt{check-yaml} pre-commit hook; CFN files were excluded
from that hook while retaining validation via cfn-lint. Both resolutions
were documented in the \texttt{CONTRIBUTING.md} for future contributors.

\section{Week 7}
\label{sec:week7}

Week~7 was dedicated to completing the CloudWatch monitoring platform
by delivering ECS and EKS dashboards, implementing structured logging
across all packages, and pushing the overall test coverage above the
80\% target.

\textbf{ECS Monitoring Dashboard:} 
I built the \texttt{ia\_ecs\_monitoring\_dashboard}
package from scratch on April~27, including health and performance
dashboards, YAML widget definitions, CloudFormation templates, export
functionality, and deploy support scripts. A key technical decision was
replacing SQL arithmetic operations in health widgets with native
\texttt{PendingTaskCount} metrics after discovering that CloudWatch
Metrics Insights does not support arithmetic in certain widget modes.
On April~30, CPU and Memory reservation widgets were added alongside a
service inventory table, giving operational teams both capacity and
inventory views in a single dashboard.

\textbf{EKS Monitoring Dashboard:} 
The EKS dashboard was
completed on April~28, then substantially revised on May~1 to switch
from custom-namespace queries to the official \texttt{AWS/EKS} control
plane metrics. The EKS discovery scope was subsequently narrowed: only
one active EKS cluster (\texttt{uipath-eks-cluster-01}, AUTOMATIONHUB

for future activation and the dashboard placed in a ready-but-deferred
state. EKS widget YAMLs were split to one file per row for consistency
with the ECS structure, and test coverage for the EKS package reached
81\%.

\textbf{Structured Logging and Test Coverage Milestone:} 
On May~1 I replaced all \texttt{print} statements and \texttt{disable\_warnings}
calls across the API, EKS, ECS, EC2, and Lambda packages with
\texttt{structlog} structured logging, providing consistent log output
across all components. The test suite was then pushed from 67\% to
81\% coverage (830 tests) in three incremental PRs, crossing the
80\% target committed in the IA Infrastructure Monitoring Platform acceptance criteria.

\textbf{Dashboard Header Standardisation and EC2 Polish:} 
Dashboard headers were standardized across all four resource types,
enforcing a consistent visual language. EC2 dashboard improvements
included Fleet Status, EBS metrics, the \texttt{AppName} fallback
for discovery, correct header height, Credit Balance widget on
the health dashboard, and annotations with AVG line on the
performance dashboard. Trailing spaces were added to markdown
headers to force CloudWatch's text widget line-break rendering.

By the end of Week~7, the CloudWatch monitoring platform was
complete across Lambda, EC2, ECS, and EKS; 830 tests passed at
81\% coverage; structured logging was consistent across all
packages; and the repository was production-merged for the
second time, closing the IA Infrastructure Monitoring Platform sub-stories.

\textbf{Technical Decisions and Constraints:} 
A key CloudWatch Metrics
Insights constraint was confirmed during ECS duration panel work: the
\texttt{GROUP BY} aggregation mode supports only AVG, SUM, MIN, and MAX
--- percentile functions (p50, p99) are not available in SQL mode. The
Metrics Insights query parser also required cluster names containing
hyphens to be substituted \emph{before} JSON serialisation; applying
substitution post-serialisation resulted in double-escaped output. Both
constraints were documented in a technical decisions log to prevent
re-investigation in later weeks. Additionally, CloudWatch Logs Insights
\texttt{put\_query\_definition} enforces a hard limit of 20 saved queries
per account, which constrained the saved-query strategy to a
\texttt{Intelligent-Automation} folder with errors-only scope.

\textbf{Key Architectural Decision:} 
The discovery of the CITCOWORKS
and MERIDIAN platforms sharing the \textbf{``Shared Cloud Artifacts''}
BudgetCode was the most significant architectural finding of the week.
A naive single-stage tag filter would conflate operationally unrelated
resources from two distinct platforms. The \texttt{AppName} discriminator
was established as a mandatory second filter stage for these two platforms,
a pattern that became the standard two-stage discovery architecture used
throughout the inventory API in subsequent months. Additionally, five of
the six Meridian ECS clusters had no resource tags at all, requiring a
cluster-name-based fallback strategy to ensure complete fleet coverage.

\section{Week 18}
\label{sec:week18}

Week~18 delivered the alarm email log group deep-link system and completed
the five-phase log group observability specification.

\textbf{Alarm Email Log Group Deep-Links (log group observability feature Phase~2):} 
The alarm
formatter Lambda was extended to auto-construct CloudWatch Logs Console
deep-link URLs from the cached log group inventory. When an alarm fires,
the formatted email now includes a direct link to the relevant log group
filtered to the alarm timestamp, eliminating the need to manually navigate
to Logs Insights and reconstruct the query. The log group URL encoding
utility was tested for all seven platform types, handling the differences
in log group naming conventions between Lambda, ECS, EC2, and MSK resources.

\textbf{Grafana CloudWatch Logs Panel:} 
A placeholder Row~17 panel was
implemented in the Grafana dashboard using the CloudWatch Logs datasource,
with a \texttt{\$platform} variable filter. This provided a foundation
for the full X-Ray tracing row planned for delivery in later weeks.

\textbf{Five-Phase Log Group Observability Specification:} 
The
log group observability feature specification was finalised covering: Phase~1 (log group discoverer
Lambda), Phase~2 (inventory API \texttt{/api/log-groups} endpoint), Phase~3
(alarm email deep-links), Phase~4 (Grafana log panel row), and Phase~5
(CloudWatch Insights saved queries). All five phases were subsequently
tracked as individual sub-tasks on the JIRA board.

\textbf{Async Inventory and Pydantic Models:} 
The inventory API
async route handler architecture was validated: \texttt{asyncio.gather()}
dispatching all discoverers concurrently via \texttt{ThreadPoolExecutor}
kept full-fleet enumeration under the 10-second non-functional requirement.
Twelve service-specific Pydantic response models were added with versioned
S3 keys (\texttt{latest.json} plus timestamped history entries).

By the end of Week~18, alarm emails included actionable log group deep-links,
the inventory API reached \textbf{99\% code coverage} with a 453-test suite,
and the log group observability specification was fully defined.

\textbf{Dynamic Alarm Architecture and X-Ray Instrumentation:} 
The dynamic
alarm provisioner Lambda replaced 17 static alarm definitions with a
data-driven approach: on each deploy it reads the full resource inventory
from S3 and creates or updates per-resource CloudWatch alarms automatically.
Nine alarm types absent from the original static set were added, including
Lambda error rate (using a CloudWatch math expression rather than a metric
alarm), MSK consumer lag (\texttt{SumOffsetLag} with thresholds 1,000/5,000),
and EC2 instance and system status checks. Concurrent alarm creation was
throttled to two \texttt{ThreadPoolExecutor} workers with an adaptive retry
strategy of up to 10 attempts, resolving \texttt{PutMetricAlarm} throttling
that had previously caused partial alarm set deployments. Lambda deployment
zip sizes grew from 9~KB to 170~KB after bundling \texttt{aws-xray-sdk}
with \texttt{patch\_all()} auto-instrumentation. The X-Ray gap analysis
established the baseline: CloudWatch monitoring alone provided
approximately 30\% parity with Dynatrace; adding X-Ray, Application
Signals, and the full Grafana stack raised this to 88\%.

All \texttt{print} statements and root-logger calls across 11 Lambda

A shared

\texttt{@log\_handler} (structured entry/exit logging with correlation IDs),
\texttt{@scheduled\_handler} (EventBridge schedule context extraction),
and \texttt{@cfn\_handler} (CloudFormation custom resource response handling).

coverage (233 tests)} through this week, with ruff reporting zero lint

A parallel structured CloudFormation
nested stack I built decomposing the flat 600-line template into six
sub-stacks: \texttt{cfn.storage} (S3, DynamoDB), \texttt{cfn.iam} (all
roles and policies), \texttt{cfn.lambda} (function definitions), \texttt{cfn.bedrock}
(agent and knowledge base), \texttt{cfn.ecs} (container task definitions),
and \texttt{cfn.monitoring} (alarms and dashboards). This structure enabled
independent stack updates and brought the deployment model in line with
the \texttt{ia-it-sre-infrastructure-monitoring-amg} nested stack pattern.

By the end of Week~21, the LLM agent had reached production-quality
code standards (100\% coverage, zero lint, zero security issues), the
nested CFN architecture was established, and the SRE naming convention
was applied platform-wide.

\textbf{EventBridge vs APScheduler Decision:} 
A 59-minute architecture
discussion with Mr.\ Leung on August~4 resolved the scheduling mechanism for
the AExeo Report UI. APScheduler had been considered but had caused memory
contention issues in a prior project. EventBridge Scheduler was selected
for its managed lifecycle ($\sim$\$1/month), stateless invocation model,
and architectural consistency with the 5-minute alarm re-notification pattern
already running in Centralized Amazon Managed Grafana (AMG) Dashboard. An IAM assistance session (1~hour~50~minutes)
followed, extracting the exact permissions required from the existing
Centralized Amazon Managed Grafana (AMG) Dashboard CloudFormation execution role:
\texttt{scheduler:CreateSchedule}, \texttt{scheduler:UpdateSchedule},
\texttt{scheduler:DeleteSchedule}, and \texttt{iam:PassRole} with the
\texttt{lambda.amazonaws.com} trust policy. The ECS task CPU and memory
were aligned to production values (512 CPU units / 1,024~MB) based on
CloudWatch utilization data from the 93-day analysis window, replacing
the development-phase values that had been left in the template
from initial scaffolding.
