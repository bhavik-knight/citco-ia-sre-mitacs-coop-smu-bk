Week~1 marked the formal start of the co-op placement with Day-1 orientation alongside co-interns Mr.\ Vadla and Ms.\ Venkataraman.

I joined the Intelligent Automation SRE team at Citco Technology Management. \textbf{AWS Tooling Introduction and Team Integration:}
I participated in an introductory call on Amazon Q and the Amazon Tools ecosystem, which included a walkthrough of the AWS developer toolchain available to the team. I familiarized myself with the Citco JIRA board (\texttt{IISS} project), read the team's active Confluence pages covering the IA platform overview, and reviewed the existing tickets on the board to understand what work was in progress before my arrival. I attended the team's daily standup for the first time and began synchronizing with Mr.\ Vadla and Ms.\ Venkataraman on our shared onboarding progress.

By the end of Week~1, all access requests were submitted and in progress, my local development environment was fully operational, and I had a solid understanding of Citco's security posture, the IA platform scope, and the team's operational rhythm.

\section{Week 2}
\label{sec:week2}

With access requests progressing through the approval queue, Week~2 shifted to intensive self-directed AWS learning. Dr.\ Pawan had confirmed that the part-time schedule would continue through mid-April while my university courses were running, so I structured these early weeks around building the AWS knowledge foundation I would need before taking on my first JIRA tickets.

\textbf{AWS Database Portfolio Study:}
I completed a structured study of the full AWS database portfolio, working through both official AWS documentation and hands-on exploration via the team's Confluence resources. For relational databases, I studied Amazon RDS (including Single-AZ and Multi-AZ high availability configurations, read replicas, and automated failover), Amazon Aurora (auto-scaling clusters and the performance advantages over standard RDS for OLTP workloads), and Amazon Redshift (columnar storage, Redshift Spectrum for semi-structured data, and its positioning as an OLAP warehouse rather than a transactional database). For NoSQL options, I studied DynamoDB (schema-less design, partition key selection, and the trade-offs between strongly and eventually consistent reads) and DocumentDB (MongoDB-compatible API, collections vs tables, and DocumentDB's use at Citco for document-oriented workloads).

\textbf{Neptune Graph Database and CitcoWorks Context:}
The Neptune graph database study was particularly relevant. I learned that CitcoWorks uses a Neptune graph database to store the full L1-to-L5 entity hierarchy of client, fund, and process relationships that governs event routing across the IA platform. I studied both Gremlin (property graph traversal using vertex/edge/property model) and SPARQL (RDF triple pattern matching for semantic data integration), understanding when each is appropriate: Gremlin for application-level graph traversal, SPARQL for standards-based semantic integration. This distinction proved relevant when I later worked on the RPA LLM Agent, which uses Neptune as a potential graph layer for Hybrid Graph-RAG retrieval.

\textbf{Caching and Time-Series Databases:}
I also studied Amazon Timestream (serverless time-series database for IoT and operational metrics), Amazon QLDB (immutable ledger database for audit-grade transaction logs), and Amazon ElastiCache including both Redis (advanced data structures, pub/sub messaging, geospatial support, cluster mode with multiple primary nodes) and Memcached (simpler multi-threaded caching without data replication). The Redis study was directly applicable to the dashboard work: the IA platform uses Redis/Valkey clusters for caching, and I built the Redis monitoring row in Week~11.

\textbf{CloudWatch and CloudFormation Foundations:}
CloudWatch and CloudFormation consumed the second half of Week~2. For CloudWatch, I studied the CMAA operational cycle (Collect, Monitor, Act, Analyze), the difference between EC2 1-minute detailed monitoring and 5-minute basic monitoring, log retention policy configuration, alarm types (metric alarms for single metrics, composite alarms for aggregated state), and EventBridge integration for alarm state routing. For CloudFormation, I covered the core IaC primitives: template structure (YAML and JSON), stack lifecycle management, and change sets for controlled update previewing. I immediately applied this knowledge in Week~3's first dashboard ticket.

By the end of Week~2, I had a working knowledge of the full AWS services landscape used by the IA platform, and I understood the CloudWatch and CloudFormation primitives I would be using extensively from Week~3 onward.

\section{Week 3}
\label{sec:week3}

Week~3 was when I transitioned from learning to active delivery, with my first assigned task: the CTI CloudWatch Pipeline Dashboard. This was a CloudWatch pipeline health dashboard for the \texttt{rpacfs1-cais-pricing-\allowbreak{}extract-genai-infrastructure} repository, specifically targeting the CAIS Pricing Extract (CTI) submission pipeline.

\textbf{Dashboard Implementation and Metrics Instrumentation:}
I began implementing the dashboard. I first added CloudWatch metrics instrumentation to the \texttt{rpacfs1-cais-pricing-\allowbreak{}extract-genai-infrastructure} codebase to track CTI submission activity through the pipeline. Rather than placing metrics calls inline throughout the business logic, I refactored the instrumentation into a dedicated metrics module, which made the instrumentation testable and maintainable independent of the pipeline logic. I created the Pipeline Health Dashboard itself with CloudWatch native widgets covering the core health signals for the CAIS pricing extract workflow. I updated the \texttt{.gitignore} to exclude virtual environment directories, pytest cache, and test artifacts---basic repository hygiene that the codebase was missing. I also updated the dashboard configuration to meet the acceptance criteria I had been given: 1-hour metric granularity, a 7-day time range, and auto-refresh enabled so the team would see live pipeline status without manual page refreshes.

\textbf{Logs Insights Investigation Widget:}
I added a technical investigation layer: a CloudWatch Logs Insights widget that enabled operators to drill into raw Lambda execution logs when the health metrics indicated a problem. The Logs Insights widget used a pattern-matched query against the \texttt{/aws/lambda/} log group prefix to surface error patterns directly in the dashboard, rather than requiring the operator to navigate to CloudWatch Logs and write a query manually. I added screenshots of the Logs Insights query setup to the pull request description so the team could reproduce the configuration in other environments.

\textbf{Testing and Code Quality:}
I completed the testing phase. I wrote unit tests for the Logs Insights query functionality, CloudFormation template validation tests (checking that the template schema was valid before deployment), and ran the full test suite to confirm no regressions. I also applied code quality improvements identified while writing the tests: moving all import statements to the top of files following Python best practices, and adding type hints to function signatures to enable better IDE support and early error detection.

By the end of Week~3, the CTI CloudWatch Pipeline Dashboard was ready for pull request review. The dashboard covered the CTI pipeline health signals, the Logs Insights investigation widget was functional, the test suite was passing, and the repository was in a clean state for code review. This was my first complete delivery cycle at Citco---task assignment to implementation to tests to pull request---and it established the quality baseline I would maintain for all subsequent work.

\section{Week 4}
\label{sec:week4}

In Week~4, the focus was on completing the IA Lambda Monitoring Dashboard,
addressing pull request review feedback, and delivering structured Lambda inventory
documentation on Confluence.

\textbf{Merging the CTI Dashboard and Pivoting to Lambda Monitoring:} 
The week opened with the successful merge of the CTI CloudWatch Pipeline Dashboard
into the \texttt{release/SRE} branch, closing the first JIRA ticket of
the co-op placement. I immediately transitioned to the IA Lambda Monitoring Dashboard, which required
building a monitoring solution covering all 51 Lambda functions across
the \texttt{rpacfs1} and \texttt{ia-bpo} platforms. Unlike the CTI
dashboard, which targeted a single pipeline, the IA Lambda Monitoring Dashboard needed to serve
the entire IA Lambda fleet with a single unified view.

\textbf{Dashboard Architecture and Widget Design:} 
I designed the dashboard
using a modular YAML widget architecture where each widget type lives in
its own file, allowing independent updates without touching surrounding
logic. Widgets covered five monitoring domains: filter info with inline
usage instructions, overview metrics (Total Invocations, Errors,
Throttles across all functions), error analysis (bar charts and a
CloudWatch Logs Insights investigation widget), duration metrics
(Average, Max, and P99 latency), and operational health metrics
(cold starts, concurrency, throttling, and memory utilization).
The unit test suite reached 21 tests covering dashboard builder
validation and widget contract enforcement.

\textbf{Pull Request Review and Refinement:} 
Mr.\ Leung conducted
a detailed pull request review. His feedback focused on widget layout usability and
filter propagation behavior. I addressed all comments, refined the
widget grid, and added test cases for edge cases identified during the
review. This review interaction introduced me to the team's standard for
dashboard quality: functional correctness was necessary but not
sufficient---the operational user experience mattered equally.

\textbf{Confluence Lambda Inventory:} 
In parallel with the
pull request review, I created the Lambda Inventory Confluence page as a supporting subtask. The published page cataloged all 51 functions
with trigger mappings (S3, SQS, EventBridge, API Gateway), memory
configurations, timeout settings, runtime versions, and \texttt{budget\_code}
allocations for cost tracking. This page became the authoritative
reference for the team during subsequent dashboard and support work.

By the end of Week~4, the CTI dashboard was merged, the IA Lambda Monitoring Dashboard
delivered a 51-function Lambda fleet view with a passing test suite, and
the Lambda inventory documentation was live on Confluence---completing
the part-time phase and setting the stage for full-time engagement.

Mr.\ Leung conducted a comprehensive session on the RPA operational model. I learned the

Mr.\ Murari introduced

time crystallized the monitoring gap I would spend the next ten weeks closing.
I also formally scoped the Grafana AMG Dashboard work during this week.

By the end of Week~5, I had completed the formal KT program, delivered
a multi-dashboard architecture refactor, and directly witnessed the production
incident that established \texttt{EstimatedMaxTimeLag} as the primary MSK
SLI and drove creation of the Centralized Amazon Managed Grafana (AMG) Dashboard.

By the end of Week~6, the CloudWatch monitoring platform covered four

from that hook while retaining validation via cfn-lint. Both resolutions
were documented in the \texttt{CONTRIBUTING.md} for future contributors.

Week~7 was dedicated to completing the CloudWatch monitoring platform
by delivering ECS and EKS dashboards, implementing structured logging

I built the \texttt{ia\_ecs\_monitoring\_dashboard}
package from scratch, including health and performance
dashboards, YAML widget definitions, CloudFormation templates, export

The EKS dashboard was
completed, then substantially revised to switch

I replaced all \texttt{print} statements and \texttt{disable\_warnings}

across all components. I pushed the test suite from 67\% to
81\% coverage (830 tests) across three incremental pull requests, crossing the
80\% target set in the IA Infrastructure Monitoring Platform acceptance criteria.

\textbf{Dashboard Header Standardization and EC2 Polish:} 
I standardized dashboard headers across all four resource types,
enforcing a consistent visual language. EC2 dashboard improvements
included Fleet Status, EBS metrics, the \texttt{AppName} fallback

By the end of Week~7, the CloudWatch monitoring platform was
complete across Lambda, EC2, ECS, and EKS; 830 tests passed at
81\% coverage; structured logging was consistent across all
packages; and the repository was production-merged for the
second time, closing the IA Infrastructure Monitoring Platform sub-stories.

\textbf{Technical Decisions and Constraints:} 
I confirmed a key CloudWatch Metrics
Insights constraint during ECS duration panel work: the
\texttt{GROUP BY} aggregation mode supports only AVG, SUM, MIN, and MAX
---percentile functions (p50, p99) are not available in SQL mode. The
Metrics Insights query parser required cluster names containing
hyphens to be substituted \emph{before} JSON serialization; applying
substitution post-serialization resulted in double-escaped output. I documented both
constraints in a technical decisions log to prevent
reinvestigation in later weeks. Additionally, CloudWatch Logs Insights
\texttt{put\_query\_definition} enforces a hard limit of 20 saved queries
per account, which constrained the saved-query strategy to an
\texttt{Intelligent-Automation} folder with errors-only scope.

agent skill definitions and role scaffolds for the multi-agent
orchestration layer. I upgraded the Python version from
3.11 to 3.14, documenting GIL removal and free-threaded mode status for the new
runtime.

By the end of Week~8, the first support rotation was complete,
the AutomationHub \texttt{budget\_code} integration and dynamic tag discovery closed the CloudWatch platform feature set,
and the centralized AMG dashboard repository was scaffolded and ready for the full
infrastructure build beginning in Week~9.

\textbf{Key Architectural Decision:} 
The discovery of the CitcoWorks
and Meridian platforms sharing the ``Shared Cloud Artifacts''
\texttt{budget\_code} was the most significant architectural finding of the week.
A naive single-stage tag filter would conflate operationally unrelated
resources from two distinct platforms. I established the \texttt{AppName} discriminator
as a mandatory second filter stage for these two platforms;
this pattern became the standard two-stage discovery architecture used
throughout the inventory API in subsequent months. Additionally, five of
the six Meridian ECS clusters had no resource tags at all, requiring a
cluster-name-based fallback strategy to ensure complete fleet coverage.
