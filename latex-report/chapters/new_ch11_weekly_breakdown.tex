\chapter{Weekly Implementation Breakdown}
\label{chap:weekly_breakdown}

This chapter documents the work delivered each week across the 24-week
co-op placement (Mar~15 -- Aug~31, 2026). Weeks~1--4 operated at part-time
intensity ($\sim$15--20~h/week) while balancing university coursework;
full-time engagement ($\sim$40~h/week) began in Week~5.

\section{Week 2: AWS Services Deep Dive (Mar~23--26)}
\label{sec:week2}

With access requests progressing, Week~2 shifted to intensive AWS services
learning. I completed a structured study of AWS database offerings: relational
options (RDS with Single/Multi-AZ deployments, Aurora auto-scaling, Redshift
for OLAP workloads), NoSQL options (DynamoDB, DocumentDB), and specialized
databases (Neptune for graph queries, TimeStream for time-series, QLDB for
immutable ledgers).

The Neptune study proved directly relevant---the CitcoWorks Knowledge Graph
uses Neptune to store L1--L5 hierarchy relationships. I learned both Gremlin
(property graph traversal) and SPARQL (RDF pattern matching) query languages,
understanding when each is appropriate: Gremlin for application-level traversal,
SPARQL for semantic data integration.

CloudWatch and CloudFormation consumed the remainder of Week~2. I studied
the CloudWatch CMAA cycle (Collect, Monitor, Act, Analyze), metric types
(EC2 1-minute detailed vs 5-minute basic), log retention policies, alarm
configuration (metric alarms, composite alarms), and EventBridge integration.
CloudFormation IaC fundamentals covered templates (YAML/JSON), stacks, and
change sets---knowledge immediately applied in Week~3's dashboard work.

\section{Week 4: Lambda Monitoring Dashboard \& Documentation (Apr~6--8)}
\label{sec:week4}

In Week~4, the focus was on completing the IA Lambda Monitoring Dashboard,
addressing PR review feedback, and delivering structured Lambda inventory
documentation on Confluence.

\textbf{Merging IISS-435 and Pivoting to IISS-455:}\\
The week opened on
April~6 with the successful merge of IISS-435 (CTI CloudWatch Dashboard)
into the \texttt{release/SRE} branch, closing the first JIRA ticket of
the co-op placement. I immediately transitioned to IISS-455, which required
building a monitoring solution covering all 51 Lambda functions across
the \texttt{rpacfs1} and \texttt{ia-bpo} platforms. Unlike the CTI
dashboard, which targeted a single pipeline, IISS-455 needed to serve
the entire IA Lambda fleet with a single unified view.

\textbf{Dashboard Architecture and Widget Design:}\\
I designed the dashboard
using a modular YAML widget architecture where each widget type lives in
its own file, allowing independent updates without touching surrounding
logic. Widgets covered five monitoring domains: filter info with inline
usage instructions, overview metrics (Total Invocations, Errors,
Throttles across all functions), error analysis (bar charts and a
CloudWatch Logs Insights investigation widget), duration metrics
(Average, Max, and P99 latency), and operational health metrics
(cold starts, concurrency, throttling, and memory utilization).
The unit test suite reached 21 tests covering dashboard builder
validation and widget contract enforcement.

\textbf{PR Review and Refinement:}\\
On April~8, Horace conducted
a detailed PR review. Feedback focused on widget layout usability and
filter propagation behavior. I addressed all comments, refined the
widget grid, and added test cases for edge cases identified during the
review. This review interaction introduced me to the team's standard for
dashboard quality: functional correctness was necessary but not
sufficient---the operational user experience mattered equally.

\textbf{IISS-461 Confluence Lambda Inventory:}\\
In parallel with the
PR review, I created IISS-461 as a subtask to document the Lambda
inventory on Confluence. The published page cataloged all 51 functions
with trigger mappings (S3, SQS, EventBridge, API Gateway), memory
configurations, timeout settings, runtime versions, and budget code
allocations for cost tracking. This page became the authoritative
reference for the team during subsequent dashboard and support work.

By the end of Week~4, IISS-435 was production-merged, IISS-455
delivered a 51-function Lambda dashboard with a passing test suite, and
the Lambda inventory documentation was live on Confluence---completing
the part-time phase and setting the stage for full-time engagement.

consumer lag alarm existed. Observing the post-incident discussion in real
time crystallized the monitoring gap I would spend the next ten weeks closing.
IISS-469 was completed this week and IISS-487 scope was formally defined.

By the end of Week~5, I had completed the formal KT programme, delivered
a multi-dashboard architecture refactor, and directly witnessed the production
incident that established \texttt{EstimatedMaxTimeLag} as the primary MSK
SLI and drove the creation of IISS-487.

\textbf{Technical Challenges Resolved:}\\
Two infrastructure issues were
resolved during the migration day. The \texttt{moto[all]} dependency
triggered SSL certificate download failures on Windows; switching to

failed the \texttt{check-yaml} pre-commit hook; CFN files were excluded
from that hook while retaining validation via cfn-lint. Both resolutions
were documented in the \texttt{CONTRIBUTING.md} for future contributors.

By the end of Week~7, the CloudWatch monitoring platform was
complete across Lambda, EC2, ECS, and EKS; 830 tests passed at
81\% coverage; structured logging was consistent across all
packages; and the repository was production-merged for the
second time, closing the IISS-482--486 family of JIRAs.

\textbf{Technical Decisions and Constraints:}\\
A key CloudWatch Metrics
Insights constraint was confirmed during ECS duration panel work: the
\texttt{GROUP BY} aggregation mode supports only AVG, SUM, MIN, and MAX
--- percentile functions (p50, p99) are not available in SQL mode. The
Metrics Insights query parser also required cluster names containing
hyphens to be substituted \emph{before} JSON serialisation; applying
substitution post-serialisation resulted in double-escaped output. Both
constraints were documented in a technical decisions log to prevent
re-investigation in later weeks. Additionally, CloudWatch Logs Insights
\texttt{put\_query\_definition} enforces a hard limit of 20 saved queries
per account, which constrained the saved-query strategy to a
\texttt{Intelligent-Automation} folder with errors-only scope.

\textbf{Key Architectural Decision:}\\
The discovery of the CITCOWORKS
and MERIDIAN platforms sharing the \textbf{``Shared Cloud Artifacts''}
BudgetCode was the most significant architectural finding of the week.
A naive single-stage tag filter would conflate operationally unrelated
resources from two distinct platforms. The \texttt{AppName} discriminator
was established as a mandatory second filter stage for these two platforms,
a pattern that became the standard two-stage discovery architecture used
throughout the inventory API in subsequent months. Additionally, five of
the six Meridian ECS clusters had no resource tags at all, requiring a
cluster-name-based fallback strategy to ensure complete fleet coverage.

\textbf{Grafana API Bootstrap and SQS Thresholds:}\\
An important
infrastructure challenge was the Grafana API key chicken-and-egg
problem: the provisioner Lambda needed an API key to provision
resources, but the key had to be created in Grafana which did not
yet exist. A hotfix series resolved this by bootstrapping the key
separately as a one-time setup step before the full deploy. The SQS
Health gauge composite logic was configured with precise thresholds
reflecting the Meridian queue operating range: 0--34,999 messages
(OK, green), 35,000--49,999 (WARNING, amber), and 50,000+
(CRITICAL, red). These thresholds were derived from the April
Meridian Incident peak queue depth of approximately nine million
messages, setting the warning level well below the incident
threshold while avoiding false positives during normal processing.
A three-hour knowledge transfer workshop with Kishor, Nathaniel,
and two additional team members (May~13, 188 minutes) provided
deep context on the Meridian operational model that informed
dashboard panel design decisions for the remainder of the co-op placement.

\section{Week 10: Dashboard Build Intensive (May~18--22)}
\label{sec:week10}

In Week~10, the focus was on building the remaining middle rows
of the Grafana dashboard, resolving CloudWatch Metrics Insights
SQL limitations, and migrating dashboard storage from Secrets
Manager to S3 to overcome payload size constraints.

\textbf{ECS, MSK, DocumentDB, Neptune, and OpenSearch Rows (May~19--20):}\\
The week opened with Row~5 (ECS APIs, ALB metrics) and Row~6 (MSK/Kafka)
on May~19. Row~5 required a multi-iteration approach to the \texttt{\$platform}
variable in \texttt{filterFieldsByName}: ALB resource names do not contain
the platform string, requiring a split between Row~4 (ECS container health)
and Row~5 (ALB traffic metrics). Row~6 MSK was migrated to Metric Insights
SQL with per-broker and per-consumer-group breakdown, and a meridian cluster
filter was added. On May~20, Rows~7--9 (DocumentDB, Neptune, and OpenSearch)
were completed with SQL migration and per-instance breakdowns. A new Aurora/RDS
Row~8 was added and the existing rows renumbered to accommodate it. The SQS
Inventory table panel with clickable AWS Console links was introduced on
May~20 to reduce incident response navigation time.

\textbf{Metric Insights SQL Percentile Limitation:}\\
During Lambda and ECS
duration panel work, I confirmed a fundamental Metric Insights constraint:
\texttt{GROUP BY} mode supports only AVG, SUM, MIN, and MAX aggregation
functions---p50 and p99 percentiles are not available via SQL. I implemented
a wildcard dimension workaround (\texttt{FunctionName:~["*"]}) for Lambda
duration percentile panels, accepting the tradeoff that idle functions
would appear in the list. This constraint was documented as a known
limitation to prevent future re-investigation.

\textbf{Secrets Manager 64~KB Limit and S3 Migration (May~25):}\\
By late
Week~10 the CloudFormation provisioner payload grew to approximately
14,720 lines as additional alarm templates were added, triggering
\texttt{SecretSizeExceededException} from Secrets Manager. I migrated
all dashboard JSON and alarm templates to S3 object storage with
AES256 server-side encryption to comply with the
\texttt{CITCO-S3ForceEncryptNoPublic} bucket policy. The provisioner
Lambda was updated to fetch content via \texttt{s3:GetObject} at
deploy time, removing the 64~KB ceiling entirely.

\section{Week 21: LLM Agent Major Refactor (Aug~3--7)}
\label{sec:week21}

Week~21 was the delivery-densest week of the co-op placement's second half,
focused on a comprehensive quality and reliability improvement programme
for the \textbf{Ask Citco RPA} LLM agent (IISS-824).

\textbf{Architectural Refactor and Structlog Migration:}\\
The 1,140-line
monolithic \texttt{event\_service/function.py} was decomposed into 8
single-responsibility modules following the Model-View-Controller pattern.
All \texttt{print} statements and root-logger calls across 11 Lambda
functions were replaced with \texttt{structlog} structured key=value logging.
Google-style docstrings with parameter and return types were added to all
public functions, and all \texttt{sys.path.insert} hacks were removed in
favour of a properly packaged module structure.

\textbf{handler\_utils Decorators and Test Milestone:}\\
A shared
\texttt{handler\_utils} module was built providing three decorators:
\texttt{@log\_handler} (structured entry/exit logging with correlation IDs),
\texttt{@scheduled\_handler} (EventBridge schedule context extraction),
and \texttt{@cfn\_handler} (CloudFormation custom resource response handling).
These decorators were applied to all eight Lambda handlers, eliminating
repeated boilerplate. The test suite grew from 60\% to \textbf{100\%
coverage (233 tests)} through this week, with ruff reporting zero lint
issues and Bandit clean on all security checks.

\textbf{Structured CFN Nested Stack:}\\
A parallel structured CloudFormation
nested stack was built decomposing the flat 600-line template into six
sub-stacks: \texttt{cfn.storage} (S3, DynamoDB), \texttt{cfn.iam} (all
roles and policies), \texttt{cfn.lambda} (function definitions), \texttt{cfn.bedrock}
(agent and knowledge base), \texttt{cfn.ecs} (container task definitions),
and \texttt{cfn.monitoring} (alarms and dashboards). This structure enabled
independent stack updates and brought the deployment model in line with
the \texttt{ia-it-sre-infrastructure-monitoring-amg} nested stack pattern.

\textbf{IISS-487 SRE Naming Convention and Metrics Live:}\\
The SRE
infrastructure repository service names, Lambda names, S3 bucket names,
and IAM role names were renamed from the \texttt{meridian} prefix to the
\texttt{ia-it-sre} convention. The inventory API was confirmed publishing
597 CloudWatch metrics live across all six platforms in DEV.

By the end of Week~21, the LLM agent had reached production-quality
code standards (100\% coverage, zero lint, zero security issues), the
nested CFN architecture was established, and the SRE naming convention
was applied platform-wide.

\textbf{EventBridge vs APScheduler Decision:}\\
A 59-minute architecture
discussion with Horace on August~4 resolved the scheduling mechanism for
the AExeo Report UI. APScheduler had been considered but had caused memory
contention issues in a prior project. EventBridge Scheduler was selected
for its managed lifecycle ($\sim$\$1/month), stateless invocation model,
and architectural consistency with the 5-minute alarm re-notification pattern
already running in IISS-487. An IAM assistance session (1~hour~50~minutes)
followed, extracting the exact permissions required from the existing
IISS-487 CloudFormation execution role:
\texttt{scheduler:CreateSchedule}, \texttt{scheduler:UpdateSchedule},
\texttt{scheduler:DeleteSchedule}, and \texttt{iam:PassRole} with the
\texttt{lambda.amazonaws.com} trust policy. The ECS task CPU and memory
were aligned to production values (512 CPU units / 1,024~MB) based on
CloudWatch utilization data from the 93-day analysis window, replacing
the development-phase values that had been left in the template
from initial scaffolding.
