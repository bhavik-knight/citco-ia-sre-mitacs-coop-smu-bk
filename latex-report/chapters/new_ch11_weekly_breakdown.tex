\chapter{Weekly Implementation Breakdown}
\label{chap:weekly_breakdown}

This chapter documents the work delivered each week across the 24-week
internship (Mar~15 -- Aug~31, 2026). Weeks~1--4 operated at part-time
intensity ($\sim$15--20~h/week) while balancing university coursework;
full-time engagement ($\sim$40~h/week) began in Week~5.

\section{Week 1: Environment Setup \& Access Onboarding (Mar~16--20)}
\label{sec:week1}

Week~1 marked the formal start of the internship with Day-1 orientation
on March~16. I met with manager Kishor Deotale for a comprehensive overview
of the team structure, project scope, and internship expectations. The team
introduction call connected me with co-interns Sridhar Vadla and Soundarya
Venkataraman, as well as senior mentors Horace (Ho Hoi Leung) and Kri
(Kristia Marie Labos).

The primary focus was establishing access to Citco's development infrastructure.
I raised access request tickets for Confluence (\#14193911), JIRA (\#14193674,
\#14193943), and BitBucket (\#14196961). AWS Core Dev access was initiated
through the IDM portal. Local development tools were installed: VSCode with
Python and AWS Toolkit extensions, Git with SSH key configuration, PyCharm,
Postman, and the Amazon Q plugin for AI-assisted coding.

On March~20, I attended a security meeting with Kishor, Ivan Carlo, and Maria
covering the BPM Control Questionnaire. This session provided foundational
knowledge of Citco's security posture: Active Directory integration for
authorization, Ping authentication (migrated from SiteMinder), penetration
testing processes, and access logging infrastructure including ELK stack,
Kibana, and ElasticSearch with 7--14 day retention policies. I also learned
about Dynatrace application monitoring for anomaly detection and alerting.

\section{Week 2: AWS Services Deep Dive (Mar~23--26)}
\label{sec:week2}

With access requests progressing, Week~2 shifted to intensive AWS services
learning. I completed a structured study of AWS database offerings: relational
options (RDS with Single/Multi-AZ deployments, Aurora auto-scaling, Redshift
for OLAP workloads), NoSQL options (DynamoDB, DocumentDB), and specialized
databases (Neptune for graph queries, TimeStream for time-series, QLDB for
immutable ledgers).

The Neptune study proved directly relevant---the CitcoWorks Knowledge Graph
uses Neptune to store L1--L5 hierarchy relationships. I learned both Gremlin
(property graph traversal) and SPARQL (RDF pattern matching) query languages,
understanding when each is appropriate: Gremlin for application-level traversal,
SPARQL for semantic data integration.

CloudWatch and CloudFormation consumed the remainder of Week~2. I studied
the CloudWatch CMAA cycle (Collect, Monitor, Act, Analyze), metric types
(EC2 1-minute detailed vs 5-minute basic), log retention policies, alarm
configuration (metric alarms, composite alarms), and EventBridge integration.
CloudFormation IaC fundamentals covered templates (YAML/JSON), stacks, and
change sets---knowledge immediately applied in Week~3's dashboard work.

\section{Week 3: IISS-435 CloudWatch Dashboard (Mar~30 -- Apr~1)}
\label{sec:week3}

Week~3 transitioned from learning to delivery with the first JIRA ticket:
IISS-435, a CloudWatch pipeline health dashboard for the
\texttt{rpacfs1-cais-pricing-extract-genai-infrastructure} repository.

On March~30, I added CloudWatch metrics instrumentation to track CTI
(CAIS Pricing Extract) submission activities within the pipeline. The
Pipeline Health Dashboard was created to provide operational visibility
into system performance. I refactored the metrics code into a dedicated
module for maintainability and added comprehensive unit tests to prevent
regressions. Repository hygiene tasks included updating \texttt{.gitignore}
to exclude virtual environments, pytest cache, and test artifacts.

March~31 focused on the technical dashboard with a CloudWatch Logs Insights
widget for deeper system analysis. This widget enabled error pattern extraction
from Lambda execution logs, providing root cause analysis capabilities that
the basic metrics dashboard lacked. I configured appropriate time ranges and
query syntax for CTI pipeline logs.

April~1 completed the testing phase: unit tests for Logs Insights query
functionality, CFN template validation tests, and a full test suite run.
Code quality improvements included moving imports to
file tops following Python best practices and adding type hints for IDE support.

\section{Week 4: IISS-455 Lambda Dashboard \& Documentation (Apr~6--8)}
\label{sec:week4}

Week~4 marked the transition from the CTI-specific dashboard to organization-wide
Lambda monitoring. IISS-435 was merged to release/SRE on April~6, and I
immediately pivoted to IISS-455: the IA Lambda Monitoring Dashboard.

The dashboard covered all 51 Lambda functions across \texttt{rpacfs1} and
\texttt{ia-bpo} platforms with a modular YAML widget architecture. Widgets
included: filter info with usage instructions, overview metrics (Total
Invocations, Errors, Throttles), error analysis (bar charts, Logs Insights
investigation), duration metrics (Average, Max, P99 latency), and operational
metrics (cold starts, concurrency, throttling, memory utilization). The
modular design enabled easy maintenance---adding a new widget required only
a new YAML file, not code changes.

On April~8, I addressed PR review feedback from senior team members and
created IISS-461, a Confluence documentation subtask. The Lambda inventory
page cataloged all 51 functions with trigger mappings (S3, SQS, EventBridge,
API Gateway), memory configurations, timeout settings, and budget code
allocations for cost tracking.

By Week~4's end, the part-time period delivered two production-ready CloudWatch
dashboards, comprehensive documentation, and a passing unit test suite. This
foundation enabled the full-time transition in Week~5 to focus on the more
ambitious Grafana AMG centralized dashboard (IISS-487).

\section{Week 5: Training Week \& Meridian Incident (Apr~13--17)}
\label{sec:week5}

Full-time engagement began. The week was designated as a formal
knowledge-transfer week with four structured sessions:

\begin{itemize}
    \item \textbf{RPA Support Model (Horace)} --- Blue Prism and UiPath
          operational model, pool/queue architecture, VPL queue monitoring
          (5~PM~EST daily), Corporate Actions three-track workflow
          (Mandatory, Voluntary, Ops Transfer), and the Follow-the-Sun
          escalation ladder.

    \item \textbf{CitcoWorks and Event Store (Bhanu Teja Murari)} ---
          CitcoWorks Knowledge Graph (L1--L5 hierarchy backed by Neptune),
          Event Routing Service and Action Processor deployment model, and
          the Event Store structured logging library (mandatory fields:
          \texttt{subject}, \texttt{process\_identifier}, \texttt{run\_id}).

    \item \textbf{Meridian Platform (Meridian team)} --- three-stage Kafka
          event pipeline (ERS → MSK topics → OpenSearch Consumer → AXI),
          six ECS clusters hosting Meridian services, and consumer lag as
          the primary health indicator.

    \item \textbf{\AE xeo Treasury Platform} --- cloud-based wire approval
          and fund movement via COMAPI and the \AE xeo Reporter Server REST
          API; key workloads used by MESO and E-Binder reconciliation.
\end{itemize}

On Apr~17 (Friday), the Meridian Incident occurred: a surge of automated
events from Citco Recs congested the OpenSearch consumption layer, causing
$\sim$9~million Kafka messages to queue. Detection latency was 3.5~hours;
full restoration took 7.5~hours. No MSK consumer lag alarm existed. This
incident directly motivated IISS-487 and established \texttt{EstimatedMaxTimeLag}
as the primary MSK SLI. IISS-469 was completed this week.
