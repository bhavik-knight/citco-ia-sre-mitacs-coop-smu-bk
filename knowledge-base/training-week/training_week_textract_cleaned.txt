# Compute & File Consolidation Notes — Training Week Summary  
  
## 1. Compute Service Limits  
  
| Service | Key Limitation |  
|---|---|  
| **AWS Lambda** | Max **15 minutes** per invocation (hard limit) |  
| **EC2** | No hard execution timeout — can run long tasks (e.g., 2+ hours) if needed |  
| **ECS Fargate** | Task provisioning/cooldown delay — if code doesn't finish within expected window, task may need to be manually killed |  
  
Fargate Cooldown Issue:**  
- Fargate has a startup/scaling delay ("cooling period") when provisioning new tasks.  
- If a task's processing logic doesn't account for this timing, the task may hang or fail to complete — requiring manual termination.  
  
---  
  
## 2. File Consolidation Process — Memory Issue  
  
### Symptoms  
- Process consumes **excessive memory**  
- Consolidation task doesn't complete cleanly → must be killed  
- Memory usage increases as more files are consolidated  
  
### Guidelines / Fixes  
- **Minimum memory**: 8 GB  
- **Instance family**: Use **R6 or above** (memory-optimized instances)  
- **Limit concurrency**: Process only **2–3 requests at a time**  
- **File size exception rule**:  
  - If an **individual file exceeds ~100–200 MB** → **do not consolidate**  
  - Send these as **standalone CSV files** instead  
- **Exception list files** → also skip consolidation, send directly  
  
### Report Type Reference — "Box Posision "  
- **Box position** refers to reports such as:  
  - **Position reports**  
  - **Cash reports**  
  - Other **box-level reports** (~600 records per report)  
- Format: **CSV**  
- Approx. size threshold discussed: **~494 MB+**  
  
### Output Handling  
- For files that skip consolidation:  
  - Export as **raw CSV**  
  - Drop directly into the designated **CSV output folder** ("CSK" folder — team-specific naming)

---  
  
## 3. Summary Rule of Thumb  
  
> - **Consolidate** only when individual files are small (< 100–200 MB).  
> - **Skip consolidation** for large files or exception-list items — send as standalone CSVs.  
> - **Use R6+ instances**, minimum 8 GB memory, to handle consolidation memory load.  
> - **Limit concurrent consolidation jobs** to 2–3 at a time.  
> - **Monitor Fargate task runtime** — build in handling for cooldown/provisioning delay to avoid killed tasks.  
> - Route large/exception files directly to the **CSV folder** rather than through consolidation.


### COMAPI Libraries (from Confluence PDFs — for context)

- **Aexeo Reporter Server - HTTP Request** — generates report via HTTP request to Aexeo Reporter Server (Python `reporter_requests.py`), `in_SourceSystem` arg tracks which process called (e.g., `RECON_EBINDER`)

#### Foundation Layer — Knowledge Graph (KG)
- **Knowledge Graph** is the backbone of CitcoWorks
- Stores all **relationships**: Products → Processes → Tasks → Sub-tasks
- Each item has: `attributes`, `attached fund`, `dependencies`, `optionals`
- KG is **synced from Optics** (source of truth for process/task structure)
  - Sync is **on-demand** (confirmed) — not fully real-time
  - Each **Friday**: team receives email and loads workflows into the KG
- **Who decides the hierarchy?** KG Loader — decides what is a subprocess vs sub-task
- **How are relationships added?** Via the KG loader sync from Optics
- **Process / Sub-process, Task / Sub-task hierarchy** decided by the KG Loader

#### Knowledge Graph Layer — Communication
```
Knowledge Graph
       ↓
Communication Layer
       ↓
   Event Service  ←→  Event Routing Service
       ↓
  Tenant (B.U.)
  Services
       ↓
  Mapping Tables
  (Area → Subject → Source → config for this system → Action Processors)
       ↓
  Code / Downstream System
  → performs some action based on events
  → Business Logic (other apps: MESO)
```

- **Observer pattern**: Event Service observes system attribute notifications
- **Event Routing Service** routes events to the correct **Action Processor (AP)**
- Each mapping row specifies: `Area`, `Subject`, `Source`, `Type`, `Action Processor`

### CitcoWorks — Action Processor & Event Routing

**In CitcoWorks, the Action Processor (AP):**
- Solves business logic based on event trigger routing
- AP can be anything that needs to be done in response to an event
- Template: update task status based on event → `Route (update status of task)`

**Scheduler:**
- Runs on **15-minute interval**, pushing/scheduling events
- Event Service **stores events** (currently a "dumping ground" — all events accumulated)
- Lot of events → API pulls list of active events from **DynamoDB**
- Where is the mapping hosted? → API, used by routing service

**Event Service:**
- Emits events to Event Routing Service
- Where does Event Service store events? → **ODL / Redis Elasticache → Kafka Q**
- The role of Event Service: observer → notifies downstream based on triggers

### Event Routing Service — API Structure

**Event Routing Service (ERS)** has multiple CRUD APIs:

| API | Purpose |
|-----|---------|
| `GET event/{uuid}` | Get event by ID |
| `POST add-route` | Map a downstream system |
| `list-tenant-routes` | List all routes for a tenant |

**Route configuration fields:**
- `consumer_id (TID)` — ID of the downstream system consumer
- `route name`, `event` (area/type)
- `advanced matching` — filter which data goes to the downstream queue
- `instance-type`, `domain`

**Filters:** `metadata.ids` — TID of router (consumer) stored somewhere?

**Downstream System (AP):**
- Consumes via Action Processor (name, e.g., `handle_socl_check`)
- `dynamic attributes` — consumer (B) wants the data
- **Can routing service do a pass-through?** → **No** (confirmed): cannot pass through without mapping
  - w/o mapping: cannot be passed if data is missing in source field → sends null (blank, not error)
  - If advanced matching has missing data → **fails** (confirmed)

**APIs for downstream:**
- `set-active-vision`
- `list-tenant-routes(id, distribute, list of routes, A.P. that this tenant has)`

**Who is responsible for transferring message to AP?**
- Listens to **Kafka consumer** → messages pushed to Q
- Event → Subject → Action Processor → Source → Type (SYSTEM) → metadata, clock, source-rpt → IDs (sub: MESO) → data → dyn_attrib (k/v pairs: client=data1, fund=data2, val=data3)
- **How event gets passed to AP** → through J routing
- **How routing service passes source event to AP** → via Kafka topic subscriber
